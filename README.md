# ContaApp RH

Aplicación de escritorio simple para gestionar empleados. Interfaz en Tkinter, datos en SQLite. Una única dependencia externa en tiempo de ejecución: **Pillow**, para procesar las fotos de empleado.

## Demo interactiva

**[Ver la demo →](https://claude.ai/code/artifact/97f17a62-3e57-4c84-8fa8-8a91f1b379ba)**

Es la forma pensada para explorar la aplicación sin instalar nada: capturas reales de la app, navegables con la misma barra lateral y la misma navegación que la interfaz de verdad, cargadas con datos de una empresa ficticia de ejemplo. No hay ninguna aplicación ni base de datos real corriendo detrás — es solo lectura, no se puede modificar ni guardar nada.

Todo lo de más abajo (instalación, compilar el `.exe`...) es para quien vaya a desplegar su propia instancia real de la aplicación, no un paso necesario para simplemente verla.

Para uso diario (no desarrollo), el acceso directo del escritorio abre un `.exe` compilado — no hace falta tener Python instalado para usar la app, solo para modificarla (ver "Compilar como ejecutable" más abajo).

## Requisitos

- Python 3.11 o superior (probado con 3.14).

## Instalación y ejecución

```
py -m pip install -r requirements.txt
py main.py
```

Los datos se guardan en `empleados.db` (SQLite), en la misma carpeta del proyecto. Se crea automáticamente la primera vez, junto con un departamento "General", un catálogo inicial de tipos de día (Vacaciones, Enfermedad, Festivo, Permiso o licencia, Ausencia injustificada) y un catálogo inicial de tareas de incorporación (Contrato firmado, Alta en Seguridad Social, Equipo entregado, Accesos creados). La primera vez que se ejecuta la app (mientras no haya ningún usuario todavía) aparece un asistente de configuración inicial que pide el nombre y NIF/CIF de la empresa y crea la primera cuenta de administrador con el usuario y contraseña que elijas — no hay ninguna credencial por defecto (ver "Inicio de sesión y usuarios" más abajo).

## Datos de prueba

```
py scripts\generar_datos_prueba.py
```

Genera `empleados_ficticios.csv` (50 empleados ficticios, editable) y carga ese mismo CSV en `empleados.db` junto con 5 departamentos y sus turnos de ejemplo, usando la misma capa de validación que la interfaz — así que todo lo cargado es tan correcto como si se hubiera creado a mano en la app. Es seguro volver a ejecutarlo: no duplica departamentos, turnos ni tipos de día ya existentes. No usar sobre una base de datos con empleados reales sin revisar antes, ya que añade los ficticios a lo que ya haya.

## Funcionalidades

**Inicio de sesión y usuarios**
- Antes de llegar a la aplicación hay que iniciar sesión con usuario y contraseña. La primera cuenta de administrador se crea desde el asistente de configuración inicial que aparece la primera vez que se ejecuta la app, con las credenciales que elija quien lo complete (ver arriba) — no hay ningún usuario por defecto.
- Las contraseñas se guardan con hash (PBKDF2-HMAC-SHA256, 260.000 iteraciones) y una sal aleatoria distinta por usuario — nunca en texto plano, y verificado con pruebas automatizadas que comprueban directamente la fila de la base de datos.
- **Dos roles**: **administrador** (ve y gestiona todo, sin restricciones) y **encargado de departamento** (asignado a un único departamento al crearlo). Un encargado queda limitado a ese departamento en Lista de empleados (incluida el alta de nuevos empleados, que solo puede asignarlos a su propio departamento), Nóminas, Fichajes, Solicitudes de ausencia y el calendario laboral — no ve datos de otros departamentos en ninguna de esas pantallas. Además no ve "Departamentos" ni "Gestionar usuarios..." en la barra lateral, y los botones "Configurar % Seguridad Social..." y "Configurar días de vacaciones..." (ajustes que afectan a toda la empresa) quedan deshabilitados en su sesión.
- **Gestión de usuarios** (solo visible para administradores, "Gestionar usuarios..." en la barra lateral): alta de nuevos usuarios (usuario, contraseña, rol y, si es encargado, su departamento) y baja de usuarios existentes. No se puede eliminar el usuario con el que se ha iniciado sesión, ni el último administrador que quede en el sistema (evita quedarse sin forma de gestionar la app). Todavía no hay edición de usuarios existentes ni cambio de contraseña desde la interfaz — habría que pedirlo si hace falta.
- **Importante — qué protege y qué no**: este inicio de sesión (y la separación por roles) es una puerta de entrada a la interfaz, no un cifrado de los datos. `empleados.db` sigue siendo un archivo SQLite normal: cualquiera con acceso al ordenador y un lector de SQLite puede abrirlo directamente sin pasar por el login ni por las restricciones de rol. Es útil para que un vistazo casual a la pantalla no muestre datos de nóminas o del calendario de otros departamentos, pero no sustituye a proteger el propio equipo (usuario de Windows con contraseña, disco cifrado, etc.) si eso es lo que se necesita.

**Navegación**
- Una sola ventana: la barra lateral (no menú superior) cambia el contenido de la misma ventana, nunca abre ventanas nuevas para navegar. Tiene un acceso a **Inicio** y **Alertas** arriba, y dos secciones grandes:
  - **EMPLEADOS** → Lista de empleados, Nóminas, Coste de personal, Plantillas de documentos..., Tareas de incorporación..., Candidatos, Organigrama, Departamentos (solo administradores), Gestionar usuarios... (solo administradores).
  - **CALENDARIO** → Calendario laboral (un botón por departamento — solo el propio si es un encargado), Fichajes, Solicitudes de ausencia, Tipos de día, Festivos...
  - Además, Exportar CSV y Salir.
- El ancho de la barra lateral (frente al contenido) y, dentro de Lista de empleados, el ancho de la lista (frente a la ficha) se pueden ajustar arrastrando el separador entre ambos — útil si algún puesto o departamento con nombre largo aparece cortado.
- La barra lateral tiene scroll vertical propio (con rueda del ratón) para cuando la ventana no está maximizada y sus botones no caben todos en alto — nunca quedan inalcanzables, solo hay que desplazarse para verlos.
- Solo se abren ventanas emergentes para acciones puntuales que necesitan un formulario propio: gestionar turnos, asignar un turno o marcar una ausencia/cierre por rango de fechas, editar el estado de un día concreto, y la gestión de departamentos/tipos de día. Todas ellas (incluida la propia ventana principal y la de inicio de sesión) se abren centradas sobre su ventana padre en vez de en la esquina superior izquierda.

**Diseño visual**
- Barra lateral en azul pizarra oscuro con el resto de la app en tonos claros — aporta color e identidad sin distraer de los datos. Un mismo color de acento (azul) marca las acciones principales (Guardar, Agregar, accesos rápidos de Inicio) frente a las secundarias (Cancelar, Cerrar), que quedan neutras. Los colores funcionales ya existentes (turnos y tipos de día en el calendario, aviso de Nóminas) no se han tocado, para no perder su significado. El blanco de tarjetas, campos y la rejilla del calendario es un blanco roto, no `#ffffff` puro — más suave a la vista.
- **Modo oscuro**: interruptor deslizante horizontal ("Modo oscuro", con el interruptor a su lado) al final de la barra lateral — el propio interruptor indica el estado (a la derecha y en azul = activado), como cualquier interruptor de móvil. El cambio se aplica al instante, sin reiniciar la app, y se recuerda entre sesiones (se guarda en la base de datos). Paleta oscura con fondo neutro tipo carbón/grafito (en vez de un azul marino sobre sí mismo) para que el acento azul destaque más. Los colores de turnos/tipos de día elegidos por el usuario no cambian con el tema (son colores de saturación media, legibles con texto oscuro siempre); el resto de la interfaz sí se adapta, incluida la rejilla del calendario y el aviso de Nóminas.
- Modo oscuro auditado con capturas reales de cada pantalla (no solo inferido leyendo el código), lo que encontró y corrigió tres contrastes rotos: los encabezados de página ("Calendario laboral — Ventas", etc.) casi invisibles por reutilizar un color pensado para otra cosa, las listas de turnos/departamentos/tipos de día dentro de sus diálogos de gestión con fondo blanco fijo y texto negro, y el separador arrastrable entre paneles sin colorear (franja gris de fábrica sobre fondo oscuro).
- Todo el estilo vive en un único sitio, `app/theme.py` (una paleta clara y una oscura), para que la app se vea consistente en cualquier pantalla sin tener que repetir colores archivo por archivo.

**Inicio**
- Pantalla de bienvenida que se muestra al arrancar la app: saludo según la hora, fecha del día, un aviso de alertas activas (si hay alguna) arriba de todo, siete tarjetas de resumen en rejilla, y ocho accesos rápidos.
- **Aviso de alertas**: si hay alguna alerta activa (ver la sección Alertas más abajo — reutiliza el mismo cálculo, `gather_alerts()`, sin duplicarlo), aparece un banner con el total, un desglose por categoría y un botón "Ver alertas". Si no hay ninguna, el banner no se muestra.
- **Siete tarjetas**: las cuatro originales (Empleados activos, Departamentos, Ausentes hoy, Cierres hoy — siempre de toda la empresa, incluso para un encargado, ver más abajo) más tres nuevas que sí se acotan por departamento para un encargado (a diferencia de las cuatro originales): Nóminas generadas este mes (con la propia cuenta de activos de su ámbito, no la cifra de toda la empresa de la primera tarjeta), Solicitudes de ausencia pendientes y Candidatos en proceso (cualquier fase salvo "Contratado"/"Descartado"). La tarjeta de nóminas se resalta si, a partir del día 29 del mes, sigue habiendo alguna sin generar — antes de esa fecha no se considera nada fuera de lo normal.
- Las cuatro tarjetas originales son siempre de toda la empresa, pero el detalle de quién está ausente o qué departamento tiene un cierre hoy se limita al propio departamento cuando quien ha iniciado sesión es un encargado — mismo criterio de alcance por rol que el resto de la app, aplicado también a esta pantalla de resumen.
- **Ocho accesos rápidos**: Lista de empleados, Nóminas, Calendario (al primer departamento visible — un encargado va directo al suyo), Alertas, Organigrama, Candidatos, Exportar CSV y, solo para administradores, Departamentos.

**Alertas**
- Una sola pantalla con siete tipos de aviso. Para empleados **activos**: **contratos que vencen** en los próximos 30 días (Temporal, Prácticas, etc. — un Indefinido nunca genera esta alerta), **cumpleaños próximos** (calcula el siguiente automáticamente, incluso si hay que pasar de diciembre a enero), **revisiones médicas próximas o ya vencidas**, **formación PRL pendiente** (desde el propio día de alta, no una cuenta atrás — ver la sección PRL más abajo), **certificaciones próximas a caducar o ya caducadas** (ver "Formación y certificaciones" más abajo — solo las que de verdad tienen fecha de caducidad; un mismo empleado puede generar varias, una por cada certificación que caduque pronto) y **salario por debajo del mínimo de su categoría profesional** (ver "Convenios colectivos" más abajo — solo para quien tiene una categoría asignada). Para empleados **de baja**: **retención RGPD** próxima a vencer o ya vencida (ver la sección RGPD/LOPDGDD más abajo) — la única de las siete que mira justo a los empleados que las otras seis excluyen. Las filas ya vencidas se resaltan en rojo para distinguirlas de las simplemente próximas. Un encargado de departamento solo ve las alertas de su propio departamento.
- El cumpleaños y la revisión médica son datos opcionales en la ficha del empleado (casilla "No indicada" si no se conocen); sin esos datos, sencillamente no generan alerta — no bloquean nada más de la app.
- El cálculo completo vive en un único sitio, `gather_alerts()` (`app/repository.py`) — esta pantalla, el aviso de Inicio y el resumen semanal por correo lo llaman los tres, en vez de repetir cada uno su propia secuencia de consultas (como ocurría antes de que existiera Inicio como consumidor adicional).

**Mi cuenta / resumen semanal por correo**
- **"Mi cuenta..."** en la barra lateral (visible para cualquiera que haya iniciado sesión, no solo administradores) permite cambiar la propia contraseña y conectar el correo de la propia cuenta para recibir el resumen semanal de alertas — evita que una alerta ya calculada se pase por alto solo porque nadie abrió la app ese día.
- Conectar el correo pide proveedor (**Gmail** u **Outlook**, de momento los dos únicos soportados), la dirección y una **contraseña de aplicación** (Gmail exige generarla en la configuración de seguridad de la cuenta con verificación en dos pasos activada; Outlook admite la contraseña normal por SMTP). No es una integración "Conectar con Google/Microsoft" tipo OAuth — eso exigiría registrar una aplicación en Google Cloud/Azure antes de poder funcionar en absoluto; esto funciona sin ningún registro externo.
- El resumen se envía **al abrir la app**, como muy pronto una vez por semana desde el último envío — no hay ningún proceso en segundo plano independiente de la app. Si el envío falla (credenciales incorrectas, sin conexión...), se avisa una vez abierta la ventana principal, sin bloquear el arranque — igual que un fallo de copia de seguridad.
- La contraseña de aplicación se guarda en la base de datos local de la app, con el mismo nivel de protección que el resto de datos sensibles ya guardados ahí (IBAN, DNI/NIE) — no cifrado aparte. Se explica así, sin adornos, en el propio diálogo de "Mi cuenta...".
- **Aviso por correo si la aplicación falla**: casilla independiente del resumen semanal ("Avisarme por correo si la aplicación falla en este ordenador"), deshabilitada hasta que hay un correo conectado, porque reutiliza esa misma conexión para enviar el aviso — sin credenciales nuevas que gestionar. Cubre tanto una excepción no controlada fuera de la interfaz (arranque, por ejemplo) como dentro de cualquier callback (clic de un botón, etc.), y se envía en segundo plano para no congelar la ventana mientras se conecta al SMTP. El correo **nunca** incluye el mensaje ni la traza del error — solo el tipo de excepción y cuándo ocurrió —, porque a diferencia del registro local (que nunca sale de este ordenador) esto sí sale por correo, y algunos mensajes de error de esta app incluyen a propósito un valor identificativo real (ver el aviso de privacidad en `app/logging_config.py`); el detalle completo se sigue consultando en el registro local de ese ordenador.

**Empleados**
- Lista con búsqueda (nombre, email, puesto), filtros por departamento y estado, columnas de **Salario anual** (formato español, ej. "32.500,50 €") y **Antigüedad** (calculada desde la fecha de ingreso, ej. "2 años, 3 meses"), y **ordenación por columnas**: clic en cualquier cabecera (Nombre, Puesto, Departamento, Salario anual, Antigüedad, Estado) ordena ascendente, un segundo clic invierte a descendente (indicador ▲/▼ en la cabecera activa) — junto a una **ficha de empleado** donde se ve y edita toda su información en el mismo sitio: no hay un formulario aparte para crear/editar.
- Ficha completa: datos personales y de contacto, **DNI/NIE (con validación de la letra de control)**, **fecha de nacimiento** (opcional, casilla "No indicada"), departamento, turno, **supervisor directo** (opcional, solo entre compañeros activos del mismo departamento — ver "Organigrama" más abajo), **encargado/a de departamento** (casilla + desplegable: marca de qué departamento es el responsable — cualquier departamento, no necesariamente el suyo propio; ver el aviso justo debajo de "Organigrama" sobre qué significa exactamente y qué NO significa), salario, fecha de ingreso (selector de calendario), **tipo de contrato** (Indefinido, Temporal, Formación en alternancia, Prácticas, Fijo-discontinuo) **con fecha de fin/renovación**, **cuenta bancaria (IBAN, con validación de formato y dígito de control)**, **número de afiliación a la Seguridad Social**, **próxima revisión médica** (opcional, casilla "No indicada"), **hijos a cargo** y **foto** (subida desde archivo, recortada/redimensionada automáticamente; si no hay foto se muestra un avatar con las iniciales).
- El DNI/NIE y el número de Seguridad Social son únicos por empleado (no se pueden guardar dos empleados con el mismo valor en ninguno de los dos); ambos campos siguen siendo opcionales para no bloquear el alta de empleados existentes que aún no los tengan registrados.
- La fecha de nacimiento (cuando se indica) debe ser coherente con la fecha de ingreso: un empleado no puede haber sido contratado antes de cumplir 16 años.
- La fecha de fin de contrato solo tiene sentido para contratos que no sean Indefinido: un contrato Indefinido nunca puede llevar fecha de fin (la casilla "Sin fecha prevista" se marca y bloquea sola), y la fecha, cuando se indica, no puede ser anterior a la fecha de ingreso.
- **Saldo de vacaciones** del año en curso en la propia ficha ("Vacaciones 2026: usa 14 de 22 días (quedan 8)"), calculado a partir de los días marcados como "Vacaciones" en el calendario — el primer año se prorratea por meses completos trabajados. Los días anuales son configurables para toda la empresa ("Configurar días de vacaciones..." desde la propia ficha). Para un empleado ya de baja, el saldo mostrado es el del año y hasta la fecha de su baja, no el año en curso ni hoy — para que no parezca que sigue generando vacaciones después de haber dejado la empresa.
- **Incorporación**: checklist de las tareas alrededor del primer día de un empleado (contrato firmado, alta en Seguridad Social, equipo entregado, accesos creados, u otras que se añadan al catálogo compartido desde "Tareas de incorporación..." en la barra lateral) directamente en la ficha — marcar/desmarcar una tarea es un solo clic sobre su casilla, y muestra la fecha en que se marcó. Una tarea que se añade al catálogo más tarde aparece de inmediato como pendiente para todos los empleados, incluidos los ya existentes, no solo para los nuevos. Se muestra para cualquier empleado, sin importar su antigüedad.
- **Documentos** adjuntos por empleado (contrato, copia de DNI, certificados, otros) directamente desde la ficha: adjuntar cualquier archivo con una categoría, descargarlo o eliminarlo. Se guardan en la propia base de datos (igual que la foto), hasta 10 MB por archivo. **"Generar documento..."**, junto a "Adjuntar documento...", crea el texto base de un documento a partir de una plantilla (ver "Plantillas de documentos" más abajo) y los datos reales de ese empleado — se puede copiar al portapapeles o guardar directamente como un documento adjunto más, con su propia categoría.
- **Historial de puesto y salario**: cada vez que se guarda un cambio de puesto y/o salario en la ficha, queda registrado automáticamente con la fecha — sin ningún paso extra ni botón que pulsar aparte de guardar como siempre. Se ve como una lista en la propia ficha (fecha, puesto, salario, nota), con la más reciente arriba; empieza con una entrada "Alta inicial" el día en que se dio de alta al empleado. Cambiar cualquier otro dato (teléfono, cuenta bancaria, etc.) sin tocar puesto ni salario no añade una entrada nueva.
- **Dar de baja a un empleado**: la casilla "Activo" ya no se edita a mano — el único camino es el botón "Dar de baja..." en la ficha, que pide un motivo (Baja voluntaria, Despido procedente/improcedente, Fin de contrato temporal, Jubilación, Fallecimiento, Otro) y una fecha (no puede ser posterior a hoy), para que un empleado inactivo nunca quede sin fecha ni motivo registrados. Antes de confirmar se ve una **vista previa en vivo del finiquito**: la parte proporcional de la paga extra en curso (calculada por meses completos desde el inicio del semestre en curso o la fecha de ingreso, lo que sea posterior) y los días de vacaciones no disfrutados hasta esa fecha (valorados al salario anual entre 365). No incluye el salario del propio mes en curso (se genera aparte, como cualquier otro mes, desde Nóminas) ni ninguna indemnización por despido, que depende demasiado del caso concreto para calcularse de forma genérica. Al confirmar, el finiquito calculado queda guardado de forma permanente y el empleado pasa a inactivo — "Ver finiquito..." lo vuelve a mostrar en cualquier momento; si el empleado se ha reactivado y dado de baja más de una vez, cada finiquito se conserva por separado y el propio diálogo deja navegar entre ellos ("Anterior"/"Siguiente", "1 de 2") en vez de enseñar solo el más reciente. "Reactivar" deshace la baja (por ejemplo, si se ha marcado por error) y limpia la fecha/motivo.
- Botón "Ver calendario..." desde la ficha, que cambia a la sección de Calendario mostrando el de ese empleado (misma ventana).
- Exportar a CSV la lista de empleados actualmente visible (respeta los filtros aplicados), incluida la cuenta bancaria.

**Nóminas** ⚠️ *ver aviso importante más abajo*
- Ficha individual por empleado y mes: bruto (con reparto en 14 pagas, incluyendo pagas extra de julio y diciembre), retención de IRPF, Seguridad Social del trabajador, neto a percibir, Seguridad Social de la empresa y coste total para la empresa.
- El IRPF se calcula con el procedimiento general de retención (tramos oficiales + mínimo personal y familiar según hijos a cargo), no un porcentaje fijo inventado.
- Los porcentajes de Seguridad Social son configurables (botón "Configurar % Seguridad Social...").
- **Complementos de este mes**: pluses (importe libre, con descripción — "Plus de transporte", "Plus de idiomas"...), horas extra (indicando horas y precio por hora — el importe se calcula solo) y anticipos (dinero ya adelantado al empleado). Se añaden/eliminan desde la propia página de Nóminas; los pluses y horas extra suman al bruto del mes (y por tanto también a la retención de IRPF/SS y al coste para la empresa, todo recalculado), mientras que los anticipos se descuentan directamente del neto a percibir (dinero que el empleado ya recibió, no del bruto ni del coste de empresa). La estimación en vivo los refleja al instante; una nómina ya generada no cambia si se añade un complemento después — hay que generarla de nuevo para que lo recoja, igual que con un cambio de salario.
- **Nóminas generadas (histórico real)**: por defecto se muestra una estimación en vivo (recalculada al vuelo si cambia el salario, hijos a cargo, los % de SS o los complementos del mes), pero el botón "Generar nómina de este mes" la congela como un registro histórico permanente — salario, hijos a cargo, % de SS y complementos quedan fijados tal como estaban en ese momento, así que un cambio posterior no reescribe silenciosamente una nómina ya generada. "Regenerar..." sustituye una nómina ya generada (pide confirmación). El histórico de cada empleado se ve debajo, con un clic en cualquier mes para volver a esa nómina.
- **Exportar SEPA (pago de nóminas)...** (solo administradores): genera un fichero SEPA estándar (pain.001, transferencia por lote) para pagar de una vez todas las nóminas **ya generadas** del mes que se esté viendo — se sube después a la banca online de la empresa, que es quien lo ejecuta; esta aplicación no envía dinero ni se conecta a ningún banco. Pide el nombre e IBAN de la propia empresa (como pagadora, se guardan para la próxima vez) y una fecha de ejecución solicitada, y muestra antes de generar nada una vista previa de a quién se va a pagar, cuánto, y quién se omite y por qué (sin IBAN registrado, o importe no positivo) — para revisarlo antes de descargar el fichero, no después. No usa una integración bancaria en vivo (Open Banking/PSD2), que exigiría certificarse como agregador antes de poder implementarse en absoluto.
- **Exportar para gestoría...** (solo administradores): CSV estructurado con todas las nóminas **ya generadas** del mes que se esté viendo (identidad fiscal, desglose completo del cálculo, IBAN) para que una gestoría externa lo revise o lo importe — separador `;` y decimales con coma, la convención habitual de hojas de cálculo en España. Deliberadamente **no** intenta replicar el formato de importación exacto de ningún programa concreto (A3, Sage, ContaPlus...): cada columna está documentada y usa los mismos números que ya se ven en esta misma página, así que siempre hay algo con lo que contrastar, pero no hay ninguna promesa de compatibilidad byte a byte con un programa que no se ha podido probar. A diferencia de la exportación SEPA, aquí no se omite ninguna fila (ni por falta de IBAN ni por importe cero): una gestoría necesita ver todas las nóminas del mes para cuadrar cuentas.

**Coste de personal**
- **"Coste de personal"** en la barra lateral: la vista agregada que faltaba entre "la nómina de una persona en un mes concreto" (Nóminas) y "¿cuánto cuesta la plantilla este trimestre, y cómo se compara con el anterior?" (la pregunta que dirección le hace a quien lleva RRHH). Una **tendencia mensual** (los 12 meses de un año, navegable con `<`/`>`) con nóminas generadas, bruto total y coste total para la empresa por mes, y — para administradores — un **desglose por departamento** del mes que se seleccione en la propia tabla mensual (un clic en cualquier fila la actualiza).
- Se calcula **solo a partir de nóminas ya generadas**, nunca de una estimación en vivo: un mes o un empleado sin nómina generada sencillamente no suma a estos totales — la columna "Nóminas generadas" indica cuántas componen cada cifra, para que un total bajo no se confunda con coste bajo cuando en realidad es que faltan nóminas por generar. Un mes sin ninguna nómina generada aparece igualmente en la tabla, con ceros, en vez de desaparecer.
- El desglose por departamento usa el departamento **actual** de cada empleado, no el que tuviera en un mes anterior si desde entonces ha cambiado de departamento — esta app no guarda historial de departamento (sí de puesto y salario), así que una persona transferida hace poco puede aparecer en su departamento nuevo incluso para meses en los que todavía estaba en el antiguo. Se explica así, sin adornos, en la propia página.
- Un encargado de departamento ve la tendencia mensual limitada a su propio departamento (sin el desglose por departamento, que no aporta nada cuando ya solo hay uno) — misma restricción por rol que Nóminas, Fichajes o el calendario laboral.

**Plantillas de documentos**
- **"Plantillas de documentos..."** en la barra lateral: texto base reutilizable para documentos (oferta, contrato, carta de baja... o cualquier otro que haga falta, el nombre de la plantilla es libre) con marcadores como `{nombre_completo}`, `{puesto}`, `{salario}` o `{fecha_ingreso}` que se sustituyen por los datos reales de un empleado concreto al generar el documento desde su ficha ("Generar documento..."). Ahorra reescribir lo mismo cada vez y reduce el riesgo de que un dato desactualizado (un salario antiguo, un puesto que ya cambió) se cuele en un documento oficial, porque siempre se rellena con lo que hay en ese momento en la ficha.
- El resultado es **texto base**, no un documento con formato final ni un PDF (eso sigue pendiente, ver el aviso sobre PDF más abajo): un marcador desconocido (por ejemplo, un error al escribirlo) se deja tal cual en el texto generado en vez de dar un error, así se ve de un vistazo si algo no se ha sustituido bien. El texto se puede editar libremente antes de guardarlo o copiarlo — es un punto de partida, no un documento cerrado.
- Crear y editar plantillas está disponible para cualquiera que haya iniciado sesión (administrador o encargado), igual que Tipos de día — no son datos de un departamento concreto, sino un catálogo compartido por toda la empresa.

**Candidatos**
- **"Candidatos"** en la barra lateral: seguimiento ligero de candidatos antes de contratar, deliberadamente simple — una lista con filtros por departamento y fase, sin un selector de vacantes propio ni un proceso de selección completo (entrevistadores, puntuaciones, etc.). El **puesto** es texto libre, igual que `Puesto` en la ficha de empleado, y no existe una entidad "vacante" aparte: una vacante es, en este modelo, simplemente un puesto + departamento.
- La **fase** (Recibido, Entrevista, Oferta, Contratado, Descartado) es una lista fija, no un catálogo editable como los tipos de día o las plantillas de documentos — a diferencia de esos casos, las fases de un proceso de selección no varían de una empresa a otra, así que no hace falta pantalla de gestión aparte. Cambiar la fase de un candidato se hace desde el mismo diálogo de alta/edición, sin una acción rápida distinta.
- El email del candidato **no** es único, a diferencia del de un empleado: la misma persona puede volver a presentarse a otra vacante, o a la misma más adelante, sin que la app lo bloquee.
- Eliminar un departamento con candidatos asignados está bloqueado, igual que con empleados — y si un departamento tiene ambos a la vez, o solo candidatos, el mensaje lo indica con precisión en vez de mencionar siempre "empleados" aunque el bloqueo sea en realidad por candidatos.
- Llegar a "Contratado" aquí no da de alta automáticamente al empleado: sigue siendo un paso manual desde Lista de empleados, a propósito, porque el alta real necesita datos (salario, tipo de contrato, fecha de ingreso...) que no tiene sentido pedir todavía en fase de candidatura.

**Organigrama**
- **"Organigrama"** en la barra lateral: quién supervisa directamente a quién dentro de cada departamento, en forma de árbol navegable (empleado → sus subordinados directos → los de estos, etc.), a partir del campo **Supervisor directo** de la ficha de cada empleado. Solo de lectura — asignar o cambiar un supervisor se sigue haciendo desde la propia ficha, no aquí.
- Un supervisor solo puede elegirse entre los **compañeros activos del mismo departamento** (nunca a sí mismo, ni a alguien de otro departamento o ya de baja), y la app rechaza cualquier asignación que cerraría un ciclo (que alguien acabe supervisando, directa o indirectamente, a su propio supervisor).
- Solo entran en el árbol empleados **activos**: alguien que ya no trabaja aquí no aporta nada a "cómo está organizado el equipo hoy". Si el supervisor de alguien se da de baja más adelante, esa persona pasa a mostrarse como raíz del árbol (no desaparece, ni dan error) — pero la ficha sigue mostrando su nombre, marcado como "(de baja)", en vez de vaciar el campo en silencio.
- Un encargado de departamento solo ve el árbol de su propio departamento (mismo alcance por rol que el resto de la app); un administrador puede cambiar de departamento con el propio selector de la pantalla.
- Deliberadamente **no** cambia quién puede aprobar una ausencia o revisar el seguimiento de alguien: eso sigue siendo cosa del administrador o del encargado de todo el departamento, como hasta ahora — el organigrama es, por ahora, solo el mapa de quién reporta a quién, no un nuevo sistema de permisos.
- **"Encargado/a de departamento"**, en la ficha de cada empleado (casilla + desplegable, justo debajo de "Supervisor directo"): marca qué persona encabeza qué departamento — a diferencia del supervisor directo, no tiene por qué ser dentro de su propio departamento, y a diferencia de un supervisor no aparece dentro del árbol de "Organigrama" en sí (es un dato de la ficha, no de la jerarquía de supervisión). **Importante — esto es puramente informativo, no da ningún permiso**: es un dato distinto y completamente independiente del rol **encargado** que sí controla permisos reales (ver "Inicio de sesión y usuarios" más arriba) — marcar aquí a alguien como encargado/a de un departamento no le crea ni le modifica ninguna cuenta de acceso a la aplicación; si esa persona también necesita entrar en la app con permisos de encargado sobre ese departamento, eso se sigue gestionando aparte, en "Gestionar usuarios...", exactamente igual que antes de que este campo existiera.

**Departamentos**
- Gestión de departamentos (alta y baja); no se puede eliminar un departamento con empleados, candidatos o usuarios (encargados de ese departamento) todavía asignados — el mensaje indica con precisión cuál o cuáles de los tres son el motivo del bloqueo.

**Copias de seguridad** (solo administradores)
- Se crea una copia de seguridad automática al abrir la aplicación, una vez al día (no vuelve a crear otra si ya existe una de hoy). También se puede crear una manualmente en cualquier momento desde "Copias de seguridad..." en la barra lateral. Se conservan las últimas 30 copias; las más antiguas se eliminan solas.
- Cada copia es un archivo `.db` independiente en la carpeta `backups/`, junto a `empleados.db` — un botón "Abrir carpeta" lleva directamente ahí. Al ser archivos aparte (no una tabla dentro de la propia base de datos), el listado de copias disponibles sigue siendo legible incluso si `empleados.db` llegara a corromperse.
- **Restaurar una copia** reemplaza todos los datos actuales por los de esa copia — antes de tocar nada, se guarda automáticamente una copia adicional del estado justo anterior a la restauración, por si la copia elegida no era la correcta. La aplicación se cierra para completar la restauración de forma segura: hay que volver a abrirla.

**Registro de auditoría** (solo administradores)
- "Registro de auditoría..." en la barra lateral muestra quién hizo qué y cuándo, para las acciones administrativas o sensibles de la app: alta/baja de usuarios y departamentos, alta/baja/baja-laboral/reactivación de empleados, eliminar un documento, aprobar/rechazar una solicitud de ausencia, restaurar una copia de seguridad, e inicios de sesión (correctos y fallidos, con el nombre de usuario tecleado incluso si no existe — útil para detectar intentos repetidos). Deliberadamente **no** registra cada edición rutinaria de un campo (cambiar un teléfono, por ejemplo): eso generaría demasiado ruido para que el registro siga siendo útil de un vistazo. El historial de puesto/salario en la propia ficha ya cubre aparte esos dos campos.
- Si el usuario que aparece en una entrada se elimina más tarde, el nombre sigue siendo legible en el registro (es una fotografía del nombre en el momento de la acción, no solo una referencia); es de solo lectura, sin forma de editar ni eliminar entradas desde la propia aplicación.

**RGPD/LOPDGDD — derechos ARCO y conservación de datos** (solo administradores)
- Derechos ARCO en un único sitio: la **rectificación** ya la cubre el formulario normal de la ficha (editar y "Guardar cambios"); **acceso**, **supresión** y **portabilidad** tienen ahora herramientas dedicadas, descritas abajo. El derecho de **oposición** no tiene una palanca técnica propia aquí — la base legal del tratamiento en un contexto laboral es principalmente contractual/legal, no consentimiento, así que una oposición se gestiona como proceso (quien lleve RRHH decide), no como un botón.
- **Exportar datos (RGPD)...** en la ficha de cualquier empleado (activo o inactivo) genera un archivo ZIP con todo lo que la aplicación guarda de esa persona: datos personales y de contrato (incluido el nombre de su supervisor directo y su categoría profesional/convenio, si los tiene), historial de puesto/salario, ausencias (todas, no solo las aprobadas), asignaciones de turno diarias, nóminas generadas, complementos de nómina, finiquitos, fichajes, formación y certificaciones, y los documentos adjuntos (ficheros reales, no solo su nombre) — un `datos.json` legible más una carpeta `documentos/`. Cubre a la vez el derecho de acceso (art. 15) y el de portabilidad (art. 20). Deliberadamente **no** incluye el registro de auditoría: es un metadato de uso del sistema (quién hizo qué), no un dato personal sobre el empleado.
- **Anonimizar datos...**, disponible solo cuando el empleado ya está dado de baja, borra de forma permanente los campos identificativos — nombre, email, teléfono, DNI/NIE, número de Seguridad Social, cuenta bancaria, fecha de nacimiento, próxima revisión médica, foto y documentos adjuntos —, pero conserva el puesto, departamento, salario, fechas y motivo de baja: la información que la normativa fiscal/laboral obliga a conservar durante varios años sigue existiendo, sin quedar atada a una identidad concreta. Es la respuesta al derecho de supresión (art. 17) para el caso más habitual, donde ese derecho choca con una obligación legal de conservación; para los casos sin esa obligación (p. ej. un alta duplicada por error) sigue existiendo el borrado completo ("Eliminar" en la ficha), sin cambios. Es irreversible — no se puede anonimizar dos veces ni recuperar los datos originales —, la app lo confirma explícitamente antes de ejecutarlo, y a partir de ese momento la ficha queda bloqueada para nuevos cambios (guardar, cambiar foto, adjuntar o generar documentos): editar a alguien ya anonimizado reintroduciría justo el tipo de dato identificativo que la propia acción acaba de borrar.
- **Años de conservación de datos**, configurable para toda la empresa (por defecto 4, en la configuración de vacaciones/ajustes generales), determina cuándo un empleado de baja aparece en Alertas bajo la categoría "Retención RGPD" como candidato a revisar para anonimizar — misma mecánica que las alertas de contrato o revisión médica, pero mirando justo a los empleados inactivos que esas otras excluyen. Es un aviso para que un humano decida; nadie se anonimiza solo.
- Ambas acciones quedan en el registro de auditoría. La de exportar incluye el nombre del empleado; la de anonimizar, deliberadamente, no — guardar el nombre original ahí dejaría esa entrada (inmutable, sin fecha de caducidad) como un registro permanente de la identidad que se acaba de anonimizar, contradiciendo el propósito de la propia acción. Solo guarda el id interno.

**PRL — formación y accidentes de trabajo**
- **Fecha de formación PRL** en la ficha (casilla "Pendiente" si aún no se ha impartido, igual que el resto de fechas opcionales). La formación PRL debe impartirse en el momento de la contratación (Ley 31/1995, art. 19), así que un empleado activo sin fecha aparece en Alertas bajo "Formación PRL" como pendiente desde el propio día de alta — no es un aviso de "esto vence pronto" como contrato/cumpleaños/revisión médica, sino de "esto ya debería estar hecho".
- **Accidentes de trabajo**, un registro por empleado (fecha, gravedad — Leve/Grave/Muy grave/Mortal —, descripción, si causó baja médica, si se notificó a la autoridad laboral) desde la propia ficha ("Registrar accidente..."). No es una herramienta de evaluación de riesgos completa — eso lo lleva normalmente un servicio de prevención externo —, solo constancia mínima de que ocurrió y de qué pasos básicos se han cumplido. Un registro puede eliminarse si se introdujo por error; eliminar queda en el registro de auditoría.
- Ambos entran en la exportación de datos (RGPD) de la ficha del empleado, igual que el resto de su historial.

**Incapacidad temporal (IT)** ⚠️ *estimación orientativa, no un cálculo oficial de prestación*
- Una baja médica ya no es solo un día marcado "Enfermedad" en el calendario (eso sigue existiendo aparte, sin cambios, para el propio cuadrante visual): **"Registrar baja (IT)..."** en la ficha abre un episodio propio con su **contingencia** (Común, Accidente de trabajo, Accidente no laboral) y fecha de baja. Solo puede haber un episodio abierto a la vez por empleado — hay que darle el alta antes de registrar uno nuevo.
- Desde **"Ver / gestionar..."** se añaden partes de **confirmación** (opcional, la última fecha registrada) y el parte de **alta** que cierra el episodio, y se ve el **desglose de quién paga qué parte del salario**: contingencia común/accidente no laboral son días 1-3 sin prestación, días 4-20 al 60% a cargo de la empresa (pago delegado) y desde el día 21 al 75%; accidente de trabajo es el propio día del accidente al 100% a cargo de la empresa y desde el día siguiente al 75% a cargo de la Seguridad Social. El desglose se calcula hasta hoy si el episodio sigue abierto, o hasta la fecha de alta si ya se cerró.
- Es una estimación (base reguladora aproximada a partir del salario bruto anual, no de las bases de cotización reales) — no sustituye el cálculo oficial de la mutua o la Seguridad Social, y **no se integra en la nómina mensual generada** (que sigue calculándose igual que siempre); es una vista informativa aparte, igual que el finiquito no toca la nómina del mes en curso. Verifica siempre con una gestoría antes de usar estas cifras para pagar una nómina real.
- Un episodio puede eliminarse si se introdujo por error; eliminar queda en el registro de auditoría.

**Formación y certificaciones**
- **"Añadir formación..."** en la ficha de cada empleado: un registro de cursos hechos y certificaciones obtenidas — carnés, idiomas, técnicas — con nombre libre, fecha de finalización y, opcionalmente, fecha de caducidad (casilla "No caduca", marcada por defecto). Un curso puntual y una certificación que caduca son, deliberadamente, la misma entidad: la única diferencia entre ambos es si tienen fecha de caducidad o no, así que no hace falta un campo de "tipo" aparte.
- La fecha de finalización no puede ser futura, pero sí muy anterior a la fecha de ingreso — a diferencia de un accidente de trabajo, una certificación (un carné, un idioma) puede haberse obtenido años antes de empezar a trabajar aquí. Si se indica caducidad, debe ser posterior a la finalización.
- Alertas incluye ahora una sexta categoría, **certificaciones próximas a caducar o ya caducadas** (mismo criterio de ventana de 30 días que el resto), solo para empleados activos y solo para las certificaciones que de verdad tienen fecha de caducidad — un curso sin caducidad nunca genera alerta.
- Un registro puede eliminarse si se introdujo por error; eliminar queda en el registro de auditoría.

**Categoría profesional y convenios colectivos** (gestión solo administradores)
- **"Convenios..."** en la barra lateral: catálogo de convenios colectivos, y dentro de cada uno, sus categorías profesionales (nombre + salario mínimo anual) — por ejemplo "Convenio Estatal de Comercio" con categorías "Oficial de primera" (18.000 €), "Auxiliar administrativo" (15.000 €), etc. Se crean, editan y eliminan libremente desde ahí.
- En la ficha de cada empleado, justo debajo de **Puesto**, un desplegable **Categoría profesional** (opcional) permite asignarle la que le corresponda, con las opciones agrupadas por convenio ("Convenio Estatal de Comercio — Oficial de primera"). El **puesto** sigue siendo texto libre, sin cambios — la categoría profesional es un dato adicional, no lo sustituye: el puesto describe qué hace la persona en el día a día, la categoría es su clasificación formal a efectos de convenio.
- El salario de cada empleado activo con categoría asignada se compara contra el mínimo de esa categoría; si queda por debajo, genera una alerta en la pantalla de Alertas (y en el resumen semanal por correo) con el importe exacto de la diferencia — ver "Alertas" más abajo. Empleados sin categoría asignada no generan esta alerta, sea cual sea su salario.
- Los datos de esta ficha entran en la exportación RGPD (`categoria_profesional`/`convenio_colectivo`, junto al resto de campos legibles como `departamento` o `supervisor_directo`).

**Autoservicio del empleado**
- En la ventana de inicio de sesión, **"¿Eres empleado? Consulta tus datos..."** abre un acceso aparte, sin necesitar ninguna cuenta de usuario: solo el email del empleado y un **PIN de 4-6 dígitos**. Con eso puede consultar, de solo lectura, su nómina más reciente (bruto, retenciones, neto), su saldo de vacaciones del año en curso y sus fichajes de este mes — sin tener que pedírselo a RRHH ni compartir el dispositivo kiosco de fichar.
- El PIN se establece (o se quita) desde la propia ficha del empleado, en una nueva sección **"Autoservicio"** al final — nadie lo elige por sí mismo, y por defecto ningún empleado tiene uno: hay que asignárselo explícitamente. Se guarda con el mismo cifrado (PBKDF2 + sal por persona) que las contraseñas de usuario, nunca en texto plano, y ni siquiera el propio modelo `Employee` lo expone — solo el repositorio puede leerlo, para compararlo.
- Solo empleados **activos** con un PIN ya asignado pueden acceder; alguien de baja pierde el acceso automáticamente, sin necesidad de quitarle el PIN a mano. Estable­cer o quitar un PIN queda en el registro de auditoría.
- Es deliberadamente de **solo lectura**: no se puede fichar, editar ningún dato, ni hacer nada más desde esta vista — fichar sigue teniendo su propio modo kiosco (página de Fichajes), y cualquier corrección real la sigue haciendo quien lleve RRHH desde la ficha.

**Desempeño: objetivos y evaluaciones**
- En la ficha de cada empleado, sección **"Desempeño"**: una lista de **objetivos** (título libre, fecha objetivo y estado — Pendiente/Cumplido/No cumplido, siempre nace en Pendiente) y, aparte, una lista de **evaluaciones** (fecha y comentarios libres, sin plantilla de puntuación fija). Son dos listas independientes, no una sola: un objetivo mira hacia adelante (una meta con fecha límite) y una evaluación es una nota de seguimiento sobre algo ya ocurrido — forzarlas en una única tabla habría mezclado dos conceptos distintos.
- **"Añadir objetivo..."** crea uno nuevo (siempre Pendiente); **"Cambiar estado..."** es la única forma de pasarlo a Cumplido/No cumplido — el título y la fecha objetivo no se editan en el sitio, si están mal el objetivo se elimina y se crea de nuevo. **"Añadir evaluación..."** solo admite crear y eliminar (una nota mal introducida por error), sin estado que cambiar.
- Ambas listas se pueden eliminar (una entrada mal introducida) y quedan en el registro de auditoría al hacerlo.

**Equipo asignado**
- En la ficha de cada empleado, sección **"Equipo asignado"**: un inventario ligero de material entregado (descripción libre — "Portátil Dell XPS", "Móvil Samsung"—, fecha de entrega y, opcionalmente, fecha de devolución). Mientras no tiene fecha de devolución, la lista muestra un guión — no hace falta un campo de "estado" aparte, la propia fecha ya lo indica.
- **"Añadir equipo..."** registra una entrega nueva; **"Marcar como devuelto..."** es la única forma de cerrarla (no puede ser anterior a la fecha de entrega, ni marcarse dos veces) — la descripción y la fecha de entrega no se editan en el sitio, igual que un objetivo o un accidente de trabajo: si están mal, se elimina y se crea de nuevo. **"Eliminar equipo"** borra un registro mal introducido por error y queda en el registro de auditoría.

**Calendario laboral — rejilla tipo cuadrante, integrada en la misma ventana**
- Turnos personalizables por departamento: nombre, horario y días de la semana en que aplica — el horario puede cruzar la medianoche (ej. 22:00 a 06:00, turno de noche) —, con **turno partido** opcional (segundo tramo horario, ej. mañana y tarde con descanso entre medias; a diferencia del horario principal, este segundo tramo debe empezar y terminar el mismo día). Cada empleado puede tener además un turno "por defecto" (opcional).
- **Asignación diaria por empleado**: a diferencia del turno por defecto, cada día de cada empleado puede llevar un turno distinto (el horario real varía día a día, no sigue un patrón semanal fijo) — se edita con un clic en la celda del día, o por rango de fechas de una sola vez respetando el patrón semanal del turno elegido.
- Tipos de día ampliables (catálogo global, no una lista fija): además de los 5 iniciales, se pueden agregar más con nombre y color, y marcar cuáles cuentan para el saldo de vacaciones (por defecto solo "Vacaciones"). Se pueden editar en el sitio (nombre, color, si cuenta como vacaciones) sin necesidad de borrar y crear de nuevo, algo que además no siempre es posible si el tipo ya está en uso.
- **Vista de cuadrante**: empleados en filas, días del mes en columnas, igual que una hoja de turnos en papel — cada celda muestra un código corto (T1, T2... para turnos; D1, D2... para tipos de día) con el color correspondiente; la leyenda al pie traduce cada código a su nombre completo y horario. El código evita que nombres parecidos se confundan en la celda (p. ej. "Turno 2" y "Turno único" truncados serían indistinguibles). **Líneas de cuadrícula** separan visualmente cada día y cada persona, para que sea fácil seguir una fila o columna de un vistazo, igual que en una hoja de cálculo. Un clic en cualquier celda abre un desplegable único para asignar turno, marcar ausencia, o dejar el día sin asignar. La rejilla ocupa el espacio disponible de la ventana (crece con ella) y sigue teniendo scroll propio si el contenido no cabe; la leyenda queda siempre pegada justo debajo, sin huecos. Cambiar de departamento (o de mes) es prácticamente instantáneo incluso con varias decenas de empleados.
- **Una sola página de calendario** dentro de la ventana principal (no una ventana por departamento): el botón de cada departamento en la barra lateral, o "Ver calendario..." desde la ficha de un empleado, cambian qué se muestra en esa página — vista de departamento (todas sus filas, con botones para gestionar turnos, asignar un turno por rango de fechas, marcar ausencias individuales por rango, y marcar cierres de departamento completo) o vista de un único empleado (una sola fila, sin los botones que no aplican a un empleado suelto).
- Prioridad de visualización en cada celda: ausencia individual > turno asignado ese día > cierre de departamento > vacío. Al asignar un turno o marcar una ausencia por rango de fechas, se omiten automáticamente los días que no coinciden con el patrón semanal del turno — el resumen indica cuántos días se marcaron y cuántos se omitieron.
- **"Marcar ausencia..." vs. "Solicitar ausencia..."**: marcar confirma el día al instante (uso directo del administrador, como hasta ahora); solicitar lo deja pendiente de aprobación — no aparece en el cuadrante ni cuenta en el saldo de vacaciones hasta que se aprueba desde "Solicitudes de ausencia" en la barra lateral. Aprobar lo confirma (igual que si se hubiera marcado directamente); rechazar lo descarta — si la solicitud había sustituido un día que ya estaba aprobado (por ejemplo, una vacación ya confirmada sobre la que alguien pide enfermedad ese mismo día), rechazarla restaura ese estado anterior en vez de dejar el día en blanco.
- **"Aplicar rotación..."**, junto a "Asignar turno...": para turnos que rotan solos (ej. Mañana-Tarde-Noche-Descanso repitiéndose semana tras semana) en vez de asignar cada día a mano. Se construye la secuencia añadiendo turnos (o "Descanso") uno a uno en el orden en que deben repetirse, y se aplica sobre un rango de fechas — el patrón se cicla día a día y **vuelve a empezar** tantas veces como haga falta para cubrir todo el rango, sin mirar el patrón semanal de cada turno (a diferencia de "Asignar turno...", que sí respeta el patrón semanal propio del turno elegido). El patrón no se guarda como plantilla reutilizable: es una secuencia que se arma en el momento para esa aplicación puntual, pensada para no tener que mantener un catálogo más solo para esto.

**Festivos importables**
- **"Festivos..."** en la barra lateral abre la gestión de **plantillas de festivos** reutilizables (nacional, autonómico, local...): se crea una plantilla, se le **importan fechas pegando una lista de texto** (una fecha `AAAA-MM-DD` por línea, con una etiqueta libre opcional — ej. `2026-01-01 Año Nuevo`; las líneas en blanco o que empiezan por `#` se ignoran, sirven para agrupar visualmente el texto pegado) y se **aplica de una vez a uno o varios departamentos** — en vez de marcar cada cierre a mano, departamento por departamento, cada enero.
- La app **no trae precargado ningún festivo "oficial"**: el calendario laboral real (nacional + el autonómico y local de cada municipio) cambia cada año y varía por comunidad/localidad, así que precargar fechas fijas sería, tarde o temprano, garantizadamente incorrecto para parte de las empresas que usen la app. En su lugar, se pega la lista ya conocida (del BOE, del ayuntamiento, etc.) una sola vez por plantilla.
- **Aplicar es no destructivo**: si una fecha de la plantilla ya tenía un cierre registrado en ese departamento (por el motivo que fuera), se deja tal cual en vez de sobrescribirlo — el resultado indica cuántos cierres se crearon y cuántos ya existían. Aplicar la misma plantilla dos veces a los mismos departamentos no duplica nada.
- Una fecha repetida dentro del mismo texto pegado se rechaza en vez de ignorarse en silencio (probablemente la misma lista pegada dos veces por error); una fecha ya existente en la plantilla se actualiza (la etiqueta nueva sustituye a la anterior) en vez de duplicarse, así que reimportar una lista corregida es seguro. Una fecha suelta se puede eliminar de la plantilla sin afectar a los cierres que ya se hayan aplicado.
- Eliminar una plantilla no afecta a los cierres que ya se aplicaron con ella — una plantilla es solo la lista de fechas de origen, no un vínculo permanente con los cierres que generó.
- Una vez un departamento tiene festivos/cierres registrados (por esta vía, o marcados a mano uno a uno con "Marcar cierre..."), el propio **selector de fecha** (el icono 📅 de "Desde"/"Hasta" al marcar o solicitar una ausencia, marcar un cierre, asignar un turno por rango, o corregir un fichaje) resalta esos días mientras se navega entre meses, con el mismo tono ya usado para "esto necesita tu atención" (el aviso de Nóminas) — para verlos de un vistazo al elegir un rango, sin tener que consultar el cuadrante en otra pantalla. El resaltado de "hoy" tiene prioridad si un día coincide con ambos.

**Fichajes — registro horario diario**
- Modo kiosko: se elige un empleado y se pulsa "Fichar entrada"/"Fichar salida" — el momento se registra al instante (solo el botón que corresponde según el estado actual está activo). El estado muestra desde qué hora está fichado y cuánto tiempo lleva, actualizado cada 30 segundos.
- Vista mensual por empleado con todos sus fichajes (fecha, hora, tipo, nota) y el total de horas trabajadas ese mes, con navegación mes a mes.
- Los fichajes de un mismo empleado deben alternar entrada/salida siempre — un turno que cruza la medianoche (p. ej. entrada 22:00, salida 06:00 del día siguiente) se calcula correctamente como un único intervalo.
- **Corrección manual**: si alguien olvida fichar, se puede añadir, editar o eliminar un fichaje con fecha y hora concretas (minuto exacto, no solo cuartos de hora) desde la propia página, sin necesidad de estar físicamente fichando en ese momento — la fecha/hora no puede ser futura, y debe mantener la alternancia entrada/salida del empleado.
- Este registro es la base para cumplir con la obligación legal de registro de jornada diaria; no sustituye por sí solo ninguna otra obligación laboral (convenio, descansos, etc.).

### ⚠️ Aviso importante sobre Nóminas

**El módulo de Nóminas es una estimación orientativa para uso interno, no una nómina oficial ni válida para presentar impuestos.** Simplificaciones deliberadas frente al cálculo real que haría una gestoría:
- Solo la escala **estatal** de retención de IRPF (Art. 101 LIRPF) — no incluye el tramo autonómico específico de cada comunidad.
- El mínimo personal y familiar solo cubre el mínimo del contribuyente y el mínimo por descendientes. **No** incluye ascendientes a cargo, discapacidad, ni el incremento por edad del contribuyente.
- Los tramos e importes usados corresponden a la normativa vigente en el momento de desarrollar este módulo (ver `app/payroll.py`) y pueden haber cambiado — la Ley de Presupuestos los actualiza cada año.
- Los porcentajes de Seguridad Social son configurables pero no representan automáticamente tu categoría de cotización (accidentes de trabajo/CNAE) real.
- Los complementos (pluses, horas extra) suman al bruto del mes y a lo retenido, pero el **tipo** (%) de IRPF sigue calculándose sobre el salario anual base, sin proyectar anualmente los complementos variables — solo el importe retenido escala con el bruto real del mes. Simplificación deliberada frente a un cálculo anual completo, que un programa de nómina real también suele aproximar así para las percepciones variables.

**Verifica siempre con una gestoría o asesor laboral antes de usar estas cifras para pagar una nómina real.** La app muestra este aviso también dentro de la propia pantalla de Nóminas.

## Concurrencia (acceso desde varios equipos a la vez)

`empleados.db` puede vivir en una carpeta compartida en red para que varios equipos usen la app al mismo tiempo. Ningún motor de bases de datos basado en un solo fichero (SQLite incluido) permite dos escrituras activas simultáneas — la pregunta relevante no es "¿pueden chocar dos escrituras?" (sí, siempre puede pasar) sino "¿qué ocurre cuando chocan?". Esto se verificó de forma empírica, no solo en teoría (dos conexiones reales escribiendo a la vez sobre el mismo fichero), antes de decidir la configuración:

- Cada conexión (`get_connection()`) fija explícitamente `PRAGMA busy_timeout = 5000`: si una escritura choca con otra ya en curso, SQLite **reintenta durante hasta 5 segundos** antes de rendirse, en vez de fallar al instante. Comprobado con dos conexiones reales: un escritor que retiene el bloqueo brevemente (las escrituras de esta app son transacciones cortas de una sola operación — típicamente milisegundos, nunca a la espera de que un usuario rellene un formulario) no hace fallar al segundo escritor, que simplemente espera su turno y tiene éxito.
- Se descartó a propósito pasar a **modo WAL** (`journal_mode=WAL`), pese a ser la recomendación habitual para mejorar la concurrencia en SQLite: comprobado que WAL mejora el caso lector-contra-escritor, pero **no** el caso escritor-contra-escritor (con WAL activo, dos escrituras que chocan se siguen bloqueando exactamente igual) — que es el caso real de esta app, donde todas las conexiones leen y escriben por igual. Además, WAL depende de un fichero auxiliar (`-shm`, memoria compartida) que **no es fiable sobre recursos compartidos de red** (SMB/CIFS) y puede corromper la base de datos; el modo por defecto (rollback journal, el que usa esta app) es el que el propio proyecto SQLite recomienda para bases de datos en unidades de red.
- **Límite conocido, documentado a propósito en vez de dejarlo en silencio**: si dos escrituras siguen chocando pasados los 5 segundos completos (un caso extremo, dado que cada escritura de esta app dura milisegundos), el error de SQLite se propaga tal cual en vez de traducirse al mensaje en español que sí muestran los errores de validación o de reglas de negocio dentro de cada diálogo. En la práctica, con el patrón de escrituras cortas de esta app, no debería llegar a darse.

## Base de datos configurable (SQLite / PostgreSQL)

Por defecto la aplicación sigue usando SQLite (`empleados.db`), sin ningún cambio de comportamiento ni de configuración adicional. Para una instalación que prefiera un servidor PostgreSQL propio (por ejemplo, una empresa que ya tenga uno integrado en su infraestructura), hay dos formas de activarlo:

**Desde la propia app (recomendado)**: como administrador, "Base de datos..." en la barra lateral. Permite elegir Local o Servidor PostgreSQL propio (host, puerto, nombre de la base de datos, usuario y contraseña), probar la conexión antes de guardar, y guarda la elección en `db_config.json` junto al `.exe` — sin tocar nada de Windows a mano. El cambio no tiene efecto hasta reiniciar la aplicación (la conexión se abre una única vez al arrancar). Ese fichero no se versiona (ver `.gitignore`) porque guarda la contraseña en texto plano, con la misma exposición que ya tenía la variable de entorno de abajo: protegido por los permisos del propio sistema operativo, no cifrado.

**Por variable de entorno** (alternativa para quien prefiera no pasar por la interfaz, o para automatizar una instalación): definir `CONTAAPP_RH_DB_URL` con una URL de conexión antes de arrancar la app:

```
set CONTAAPP_RH_DB_URL=postgresql://usuario:contraseña@servidor:5432/empleados
py main.py
```

Si se ha guardado un ajuste desde "Base de datos...", ese fichero tiene prioridad sobre esta variable — incluida una elección explícita de "Local", que gana aunque la variable de entorno siga definida con otra cosa. Sin ninguna de las dos cosas definidas, `get_connection()` se comporta exactamente igual que siempre (SQLite, misma ruta, mismo `PRAGMA busy_timeout` explícito de la sección "Concurrencia"). Con cualquiera de las dos, conecta a PostgreSQL en su lugar y crea ahí el mismo esquema (28 tablas) traducido a su sintaxis.

**Cómo funciona (`app/db_engine.py`)**: en vez de reescribir las más de 230 consultas SQL ya existentes en `repository.py` a un lenguaje de expresiones nuevo, se construyó una capa de adaptación fina: dos `Protocol` estructurales (`DbConnection`/`DbCursor`) que tanto `sqlite3.Connection` como una nueva `PostgresConnection` cumplen sin herencia, y una traducción de parámetros posicionales `?` (estilo sqlite3) a parámetros con nombre `:p0`, `:p1`... (lo único que acepta `sqlalchemy.text()` sin atarse a un driver concreto) que ocurre solo en el momento de ejecutar cada consulta, consciente de literales de texto (un `?` dentro de una cadena entre comillas no se traduce por error). El resultado: las mismas ~230 consultas, palabra por palabra, funcionan sin ningún cambio contra cualquiera de los dos motores.

**Traducción de esquema**: `POSTGRES_SCHEMA_TABLES` es la traducción manual, tabla por tabla, de `SCHEMA_TABLES` a sintaxis PostgreSQL — entre otras diferencias, `AUTOINCREMENT` → `GENERATED ALWAYS AS IDENTITY`, `REAL` → `DOUBLE PRECISION` (el `REAL` de SQLite ya es de doble precisión, a diferencia del `REAL` de Postgres, que no lo es), `BLOB` → `BYTEA`, `TEXT ... COLLATE NOCASE` → la extensión `CITEXT`, y `CHECK(x GLOB 'patrón')` → `CHECK(x ~ '^patrón$')` (expresión regular POSIX; las clases de caracteres de GLOB, ej. `[0-2][0-9]`, ya son sintaxis válida de expresión regular). `cursor.lastrowid`, que el driver de PostgreSQL no ofrece, se sustituye por `SELECT lastval()` inmediatamente después de cada `INSERT`.

**Verificado contra un PostgreSQL real**, no solo por diseño y revisión: `tests/test_postgres_integration.py` es una suite de integración real (conexión de red real, SQL real) contra un servidor PostgreSQL 17.10 — opt-in vía la variable `CONTAAPP_RH_TEST_POSTGRES_URL` (se salta por defecto, no hay ningún servicio PostgreSQL en CI), pensada para levantarse contra un servidor local desechable (p. ej. los binarios en zip de EnterpriseDB, sin instalador ni servicio de Windows) cuando alguien vuelva a tocar este camino. Cubre: creación del esquema completo desde cero, login case-insensitive, traducción de duplicados y de violaciones de clave foránea a los mismos mensajes en español que SQLite, CRUD con id autogenerado, y búsqueda case-insensitive. Esa primera ejecución real (nunca antes hecha) encontró y corrigió tres bugs que ningún test contra SQLite podía detectar: una cláusula `COLLATE NOCASE` inválida en Postgres que rompía el login (`repository.py`), `lastrowid` siempre en `None` porque `result.is_insert` de SQLAlchemy no reconoce SQL en texto plano como un INSERT, y `lastval()` abortando la transacción entera cuando un INSERT no genera ningún valor de secuencia (ambos en `app/db_engine.py`, ver su docstring para el detalle). El camino SQLite, en paralelo, sigue estando probado byte a byte por la suite completa (1497 pruebas, más las 7 de integración PostgreSQL — 1504 en total) ejecutándose sin ningún cambio de comportamiento a través de esta misma capa.

**Lo que NO cambia de motor**: las copias de seguridad (`BackupRepository`, API de backup en caliente exclusiva de `sqlite3.Connection.backup()`) solo están disponibles con SQLite — con `CONTAAPP_RH_DB_URL` definida, `main.py` no las construye (`backups = None`) y la app deshabilita "Copias de seguridad..." en la barra lateral en vez de fingir que la función existe; una instalación con su propio PostgreSQL ya suele tener, a ese nivel, su propia estrategia de copias.

## Desarrollo

Instalar dependencias de desarrollo (pytest, mypy, pyflakes):

```
py -m pip install -r requirements-dev.txt
```

Ejecutar la suite de pruebas:

```
py -m pytest
```

Verificar tipado estricto e imports/nombres sin usar:

```
py -m mypy --strict app main.py scripts tests
py -m pyflakes app main.py scripts tests
```

**Control de versiones**: el proyecto usa git. Tras clonar, activa el hook de pre-commit (no viaja solo con el repositorio, hay que copiarlo una vez):

```
cp scripts/pre-commit .git/hooks/pre-commit
```

A partir de ahí, cada `git commit` ejecuta automáticamente mypy --strict, pyflakes y la suite completa, y aborta el commit si algo falla.

## Compilar como ejecutable (.exe)

El acceso directo del escritorio apunta a un `.exe` independiente (compilado con PyInstaller), no a `pythonw.exe main.py` directamente -- así se abre con doble clic sin depender de que Python siga instalado en esa misma ruta. Para volver a compilarlo tras un cambio (usa el `.spec` ya generado, que recuerda las opciones de empaquetado, pero **no** recuerda `--distpath`: es un flag exclusivo de línea de comandos, hay que repetirlo cada vez):

```
py -m pip install -r requirements-dev.txt
py -m PyInstaller "ContaApp RH.spec" --distpath .
```

El `.exe` resultante se genera **en la raíz del proyecto**, junto a `empleados.db` -- a propósito, no en una subcarpeta `dist/`: `app/database.py` calcula `DEFAULT_DB_PATH` junto al propio ejecutable cuando corre compilado (`sys.executable`, no `__file__`, que en una compilación de un solo archivo apunta a una carpeta temporal de autoextracción distinta en cada arranque), así que el `.exe` debe seguir viviendo en la misma carpeta que la base de datos real para encontrarla. Si algún día se mueve el `.exe` a otra carpeta, hay que mover `empleados.db` (y `backups/`) con él. **Olvidar `--distpath .` es un error real, no solo teórico**: sin él, PyInstaller genera el `.exe` en `dist/` en vez de la raíz, y al abrirlo desde ahí crea una `empleados.db` nueva y vacía en vez de encontrar la real -- pasó exactamente así durante el desarrollo de este mismo proyecto.

Recompilar desde cero (por ejemplo, si se regenera el `.spec` a mano) usa la misma idea:

```
py -m PyInstaller --onefile --windowed --name "ContaApp RH" --distpath . main.py
```

Aviso esperable la primera vez que se ejecuta un `.exe` recién compilado (sin firma digital): Windows SmartScreen o el antivirus pueden mostrar un aviso de "editor desconocido" -- es normal en binarios sin firmar, se permite la ejecución y no vuelve a preguntar.

```
  alerts.py             Cálculo puro de alertas: contratos por vencer, cumpleaños próximos, revisiones médicas próximas o vencidas, formación PRL pendiente, certificaciones próximas a caducar y revisión de retención RGPD para empleados de baja
  alerts_ui.py           Página de Alertas: lista combinada de las cinco, vencidas resaltadas en rojo
main.py               Punto de entrada (seeds iniciales + login + envío del resumen semanal si corresponde, antes de la ventana principal)
scripts/              Utilidades de desarrollo (generación de datos de prueba)
tests/                Pruebas automatizadas (validación, repositorios, widgets, fotos, nómina)
```

## Diseño pensado para minimizar errores

- Todas las consultas SQL usan parámetros (sin concatenación de strings), evitando inyección SQL.
- Restricciones a nivel de base de datos (`NOT NULL`, `CHECK`, `UNIQUE`, claves foráneas) además de la validación en Python: los datos inválidos no pueden persistirse aunque haya un fallo en la capa de validación.
- Claves foráneas con acción explícita según el caso: `RESTRICT` para no poder borrar un departamento con empleados asignados, ni un turno con días ya asignados en el cuadrante (evita perder historial de calendario sin avisar); `CASCADE` para que los turnos y cierres de un departamento, o las asignaciones diarias de un empleado, se limpien si el departamento/empleado se elimina; `SET NULL` para que borrar un turno solo desasigne el turno "por defecto" de los empleados en vez de bloquear el borrado.
- Migraciones de esquema automáticas y seguras: si se abre una base de datos creada por una versión anterior de la app, se le añaden las columnas y tablas nuevas sin perder datos existentes.
- Las copias de seguridad se crean con la API de backup en caliente de `sqlite3` (`Connection.backup()`), pensada precisamente para copiar una base de datos mientras está en uso, en vez de copiar el archivo a pelo con riesgo de capturarlo a medio escribir. Restaurar una copia nunca sustituye `empleados.db` mientras la aplicación lo tiene abierto (en Windows, sustituir un archivo bajo una conexión activa no es fiable): se deja preparada y `main.py` la aplica en el único momento seguro, justo antes de abrir ninguna conexión, en el siguiente arranque. El nombre de cada copia incluye microsegundos, no solo hasta el segundo, para que dos copias creadas en rápida sucesión (como ocurre al restaurar: primero se guarda una copia de seguridad del estado actual, después se lee la copia elegida) nunca puedan coincidir de nombre y una sobrescribir a la otra en silencio.
- Toda operación de escritura ocurre dentro de una transacción con rollback automático ante errores.
- Fechas y horas siempre mediante selectores (calendario, combos de hora, checkboxes de días), nunca texto libre — elimina de raíz los errores de formato en vez de solo detectarlos.
- El interruptor de modo oscuro y la rejilla completa del calendario (cabecera, columna de nombres, líneas de cuadrícula y celdas) están dibujados a mano sobre un Canvas en vez de con widgets de Tk reales por celda — Tkinter/ttk no trae de fábrica ni un interruptor deslizante ni una rejilla con líneas visibles, pero además, para la rejilla, hay un motivo de rendimiento: perfilado aparte confirmó que un widget real (`tk.Label`) por celda era el cuello de botella genuino al cambiar de departamento (~400-750 ms con varias decenas de empleados × 31 días — ni las consultas SQL, de menos de 2 ms, ni la propia creación de los widgets, sino el paso de layout/render interno de Tk), mientras que dibujar el mismo resultado visual como rectángulos y texto de canvas tarda 15-20 veces menos (~30-90 ms), sin añadir ninguna dependencia nueva en ningún caso.
- IBAN validado con el dígito de control real (algoritmo mod-97), no solo el formato. DNI/NIE validado con la letra de control real (algoritmo mod-23), también más allá del formato. El número de Seguridad Social solo se valida en formato (12 dígitos) — el algoritmo oficial de su dígito de control tiene un caso especial no confirmado con certeza suficiente, y validarlo mal rechazaría números reales válidos.
- La foto (y los documentos adjuntos) se guardan en la propia base de datos (no en archivos sueltos que se puedan perder o desincronizar); las consultas de listado excluyen ese contenido a propósito para no cargar todos los bytes en cada búsqueda — solo se piden al abrir la ficha de un empleado concreto o al descargar un documento en particular.
- Contraseñas con hash PBKDF2-HMAC-SHA256 (260.000 iteraciones) y sal aleatoria distinta por usuario, comparación en tiempo constante al verificar (evita ataques de temporización) — nunca se guarda ni se compara la contraseña en texto plano. Sin dependencias externas de criptografía: todo con `hashlib`/`hmac`/`secrets` de la biblioteca estándar.
- La restricción por rol (encargado limitado a su departamento) se aplica en la propia consulta a la base de datos en cada página afectada, no solo ocultando opciones en la interfaz: aunque el desplegable de departamento se deshabilita y se reduce a una sola opción, el método que decide qué se consulta ignora el desplegable por completo y usa siempre el departamento fijado al iniciar sesión — así un fallo o manipulación del propio combo no podría filtrar datos de otro departamento.
- El cálculo de alertas está aislado en `app/alerts.py` como funciones puras (sin UI ni base de datos), igual que `payroll.py`/`vacation.py`/`time_tracking.py`. La migración que añade fecha de nacimiento y próxima revisión médica no intenta rellenar esos datos para empleados ya existentes (a diferencia del historial de puesto/salario, aquí no hay ningún valor honesto que inferir) — sencillamente no generan alerta hasta que se rellenan a mano.
- Los complementos de nómina siempre se guardan con importe positivo (nunca un signo negativo escondido en el dato); es el tipo (plus/horas extra frente a anticipo) el que decide en el cálculo si suma o resta — evita el error de guardar un anticipo como "-300" y que alguien lo sume por error en vez de restarlo. El importe de las horas extra nunca se teclea directamente: se guarda calculado (horas × precio/hora) para que no pueda quedar inconsistente con su propio desglose.
- El historial de puesto/salario nunca modifica una entrada ya guardada, solo añade nuevas ("historial con fecha de efecto": cada entrada dice "desde esta fecha, esto era así", sin fecha de fin explícita, implícita por la siguiente entrada o por "sigue vigente" si es la más reciente) — así una entrada antigua nunca puede reescribirse ni perder su valor original, igual que el histórico de nóminas generadas.
- Dar de baja a un empleado no se hace a través del formulario general de edición: es un método propio (`terminate()`), con su fecha y motivo obligatorios, para que "inactivo" nunca sea un estado sin explicación guardada — la casilla de activo/inactivo de versiones anteriores se ha retirado precisamente por eso. El finiquito calculado se guarda como histórico que solo añade, nunca sustituye (mismo criterio que el historial de puesto/salario, no el de "regenerar sustituye" de las nóminas generadas), porque una baja no es un hecho recurrente y corregible mes a mes.
- El registro de auditoría guarda el nombre de usuario como texto en el momento de la acción, no solo una referencia al usuario: si esa cuenta se elimina más tarde, el "quién" del historial se sigue pudiendo leer. Sabe qué usuario está actuando ahora mismo porque `main.py` se lo indica una única vez justo después de iniciar sesión, en vez de que cada pantalla/diálogo que audita algo (una decena, repartidos por toda la app) tenga que recibirlo por separado en su propio constructor.
- El `CHECK` de `audit_log.action` empezó como una lista cerrada de códigos válidos; se cambió a "no vacío" (con la lista real viviendo solo en las constantes `AUDIT_*` de Python) porque SQLite no permite ampliar un `CHECK` ya existente con `ALTER TABLE` — cada acción nueva habría exigido recrear la tabla entera. Se hizo una sola vez, antes de que RGPD necesitara dos códigos más, en vez de repetir esa migración cada vez que se audita algo nuevo en el futuro.
- Anonimizar un empleado es un método propio (`anonymize()`), no una rama más de `update()`, con sus propias reglas: exige que el empleado esté de baja (no tiene sentido anonimizar a alguien en plantilla) y no permite anonimizar dos veces (una columna `anonymized` dedicada, no una inferencia a partir de qué campos están vacíos — un empleado real con DNI/NIE sin rellenar todavía no debe confundirse con uno ya anonimizado). Por el mismo motivo que el registro de auditoría evita registrar cada edición rutinaria, la propia entrada de auditoría de esta acción guarda el id del empleado pero **no** su nombre: guardarlo dejaría el registro (inmutable, sin caducidad) como una segunda copia permanente de la identidad que se acaba de anonimizar.
- La exportación de datos RGPD (`data_export.py`) reutiliza los mismos repositorios que el resto de la app en vez de tener su propio SQL: `list_all_for_employee()` en ausencias/asignaciones/complementos/fichajes existe aparte de los métodos ya existentes (`get_for_month()`, `list_for_date()`, etc.) porque esos filtran por periodo o por estado aprobado — el derecho de acceso necesita todo, sin filtrar nada.
- Tipado estático completo, verificado con `mypy --strict`; sin imports ni nombres sin usar, verificado con `pyflakes`.
- La contraseña de aplicación de la cuenta de correo conectada vive aparte del propio `User` (un `EmailConnection` que solo se lee cuando de verdad hace falta usarlo — enviar el resumen, o mostrar el diálogo de Mi cuenta), igual que `password_hash`/`salt` nunca viajan en `User`: un secreto reversible no debe fluir por rutas de código que solo necesitan saber "quién es el usuario actual". El envío del resumen semanal usa `smtplib`/`email` de la biblioteca estándar contra el SMTP del proveedor conectado — sin ninguna dependencia nueva, ni una integración OAuth que hubiera exigido registrar una aplicación en Google Cloud/Azure antes de poder funcionar en absoluto.
- Cambiar la propia contraseña exige la contraseña actual (autoservicio real, no algo que un admin pueda hacerle a otra cuenta sin conocerla — para eso ya existe borrar y volver a crear el usuario); un intento con la contraseña actual incorrecta se rechaza sin tocar la contraseña existente, verificado explícitamente.
- Un episodio de incapacidad temporal es una entidad propia (`it_episodes`), no una fila más de `employee_absences` — marcar "Enfermedad" en el calendario sigue existiendo igual, sin cambios, para el cuadrante visual; son dos sistemas deliberadamente desacoplados, no fusionados en una sola acción como sí ocurre al dar de baja a un empleado (que sí crea el finiquito a la vez). Solo puede haber un episodio abierto por empleado (`get_open_episode_for_employee()` se comprueba en `create()`), para que "de baja por IT" sea siempre un estado inequívoco. El desglose de pago (`app/incapacidad_temporal.py`) es deliberadamente informativo aparte, no se integra en `calculate_monthly_payroll()`: esa función asume un mes completo trabajado, y repartir sus parámetros para modelar días parciales de IT dentro de un cálculo ya extensamente probado se juzgó un riesgo mayor que el beneficio frente a una vista de desglose separada — mismo criterio que el finiquito, que tampoco toca la nómina del mes en curso.
- El cálculo de nómina está aislado en `app/payroll.py` como funciones puras (sin UI ni base de datos), con tests que verifican monotonía (más salario → más retención, más hijos → menos retención, y el neto a percibir nunca debe caer bruscamente solo por ganar un euro más de bruto) y consistencia aritmética además de un caso de referencia — y con las simplificaciones/limitaciones documentadas en el propio módulo, no ocultas. Esta última propiedad de monotonía no era solo teórica: `reduccion_rendimientos_trabajo()` saltaba a `0.0` nada más superar el umbral alto del Art. 20 LIRPF en vez de al suelo real (`REDUCCION_RENDIMIENTOS_MIN`), una discontinuidad de ~2.364 € en la base imponible justo en ese punto que un barrido completo de 10.000 a 60.000 € de salario confirmó como un caso real, no de laboratorio, antes de corregirla.
- La alerta de formación PRL pendiente es la única, junto con la de retención RGPD, que no avisa de "esto vence pronto": la formación debe impartirse en el momento de la contratación, así que su fecha de referencia es la propia fecha de ingreso — un empleado sin formación aparece como pendiente desde el primer día, no con una cuenta atrás. El registro de accidentes de trabajo permite crear y eliminar (una entrada mal introducida por error) pero no editar en el sitio, a diferencia del historial de puesto/salario o el finiquito, que son estrictamente de solo-inserción: un accidente es un hecho registrado por una persona que puede necesitar corregirse, no un cálculo derivado.
- La ficha de un empleado tiene scroll vertical propio (`app/calendar_widget.py`'s `ScrollableFrame`, el mismo componente ya usado por la barra lateral) porque, entre los campos del formulario y las secciones de Documentos/Historial/Accidentes de trabajo, el contenido dejó de caber en el alto por defecto de la ventana (1200×680) — sin scroll, esas tres secciones quedaban completamente inalcanzables, no solo recortadas, sin importar cuánto se maximizara la ventana.
- Generar un documento (`app/document_templates.py`) no crea ningún registro propio ni una tabla paralela de "documentos generados": produce texto en memoria que, si se guarda, pasa por el mismo `EmployeeDocumentRepository.upload()` que un archivo subido a mano — una vez guardado es indistinguible de cualquier otro documento adjunto (misma descarga, mismo borrado, misma inclusión en la exportación RGPD), en vez de duplicar ese almacenamiento/gestión para una segunda categoría de "documento". La sustitución de marcadores deliberadamente no usa `str.format()`: un marcador desconocido (typo al escribirlo) se deja tal cual en el texto en vez de lanzar una excepción, porque quien escribe una plantilla de RRHH no tiene por qué depurar un traceback de Python — el propio texto generado, con `{salarioo}` visible en medio, ya es la señal de que algo está mal escrito.
- El checklist de incorporación (`OnboardingTaskRepository`) no guarda una fila por tarea al crear un empleado: el estado hecho/pendiente de cada tarea se calcula al vuelo con un `LEFT JOIN` entre el catálogo y las tareas ya marcadas para ese empleado (mismo patrón que el desglose por departamento del coste de personal), así que una tarea añadida al catálogo más tarde aparece de inmediato como pendiente para todos los empleados — incluidos los que ya estaban dados de alta — sin ningún proceso de relleno retroactivo. Desmarcar una tarea borra su fila en vez de guardar un booleano a `False`: solo existe una fila para lo que de verdad está hecho. Eliminar una tarea del catálogo que ya tiene alguna marca está `ON DELETE RESTRICT` en vez de en cascada — el mismo criterio ya usado para `day_type_id` en cierres/ausencias (no se puede eliminar un tipo de día en uso): perder en silencio el registro de que algo ya se hizo, solo porque se quiso quitar del catálogo, sería peor que obligar a dejarlo o a desmarcarlo primero.
- El informe de coste de personal (`PayrollRecordRepository.monthly_totals()`/`department_totals()`) se agrega exclusivamente a partir de `payroll_records` (nóminas ya generadas), nunca de un cálculo en vivo con el salario actual: para meses pasados, el salario actual de un empleado puede no ser el que tenía entonces (y esta app no guarda un histórico completo por mes para reconstruirlo con certeza para cualquier fecha), así que estimar "hacia atrás" arriesgaba mostrar una cifra plausible pero incorrecta a dirección — el mismo motivo, aplicado a este informe, por el que las plantillas de festivos no traen fechas precargadas ni el número de Seguridad Social valida su dígito de control. `COALESCE(SUM(...), 0)` en SQLite devuelve un `int` cuando no hay ninguna fila que sumar (un departamento sin nóminas ese mes) pero un `float` en cuanto hay al menos una — descubierto al inspeccionar el resultado real de una consulta de prueba antes de dar por bueno el método, no asumido; ambos métodos envuelven explícitamente el resultado en `float(...)` para que `MonthlyCostSummary`/`DepartmentCostSummary` cumplan su tipo declarado también en el caso de suma vacía, no solo en el caso general. Tanto la tendencia mensual (siempre 12 filas, meses sin nóminas a cero) como el desglose por departamento (`LEFT JOIN` desde `departments`, no `JOIN`) devuelven deliberadamente ceros en vez de omitir la fila entera cuando no hay datos, para que un hueco se lea como un hueco y no desaparezca de la vista.
- Las plantillas de festivos (`HolidayTemplateRepository`) deliberadamente no traen ninguna fecha "oficial" precargada: a diferencia del DNI/NIE o el IBAN (algoritmos de control fijos y verificables), el calendario de festivos real cambia cada año y varía por comunidad/localidad, así que cualquier fecha fija incrustada en el código quedaría mal tarde o temprano para parte de las empresas que usen la app — el mismo criterio que ya evitó implementar el dígito de control del número de Seguridad Social sin poder verificarlo con certeza. Aplicar una plantilla a un departamento es intencionadamente no destructivo (`INSERT ... ON CONFLICT DO NOTHING`, verificado con una prueba dedicada de que `cursor.rowcount` distingue una fila insertada de una omitida): una fecha con un cierre ya registrado por otro motivo se deja tal cual en vez de sobrescribirla, así que aplicar la misma plantilla varias veces (o a un departamento que se añade más tarde) nunca duplica ni pisa datos existentes.
- El resaltado de festivos en el selector de fecha (`CalendarPopup`/`DateEntry`, parámetro `marked_dates`) lee exclusivamente `DepartmentClosureRepository.list_dates_for_department()` — los cierres que el propio departamento ya tiene registrados, vengan de una plantilla aplicada o de "Marcar cierre..." a mano — nunca una fecha "oficial" incrustada en el código, por el mismo motivo ya explicado para las plantillas de festivos. `list_dates_for_department()` deliberadamente no acota por mes/año (a diferencia de `get_for_month()`, que sí): el selector necesita poder resaltar el mes al que se navegue con "◀"/"▶" sin volver a consultar la base de datos en cada clic. Cada uno de los cuatro diálogos que abren un `DateEntry` de rango (marcar/solicitar ausencia, marcar cierre, asignar turno) y la corrección manual de fichajes resuelve su propio `marked_dates` a partir de datos que ya tiene en la mano (el departamento del primer empleado de la lista, o el empleado directamente) — sin necesitar un parámetro nuevo en ninguna llamada existente desde `calendar_page.py`.
- `candidates.department_id` es `ON DELETE RESTRICT`, igual que `employees.department_id` (comprobado contra ese precedente directamente en `database.py`, no asumido): un candidato no debe desaparecer en silencio solo porque se elimina el departamento al que aspira. Eso convirtió a `DepartmentRepository.delete()` en un método con dos posibles bloqueos en vez de uno, y dejó al descubierto un bug ya existente: el mensaje de error asumía que cualquier `IntegrityError` era por empleados, así que un departamento sin empleados pero con candidatos mostraba igualmente "hay empleados asignados" — incorrecto. El mensaje de `IntegrityError` de SQLite (`FOREIGN KEY constraint failed`) no incluye tabla ni columna (comprobado con un script suelto antes de descartar esa vía), así que no se podía distinguir el caso mirando el texto del error: se resolvió con comprobaciones explícitas (`has_employees`/`has_candidates`) antes de intentar el borrado, con tres mensajes distintos según el caso, dejando el `try`/`except` original como red de seguridad genérica para cualquier otra referencia futura no contemplada.
- El **puesto** de un candidato es texto libre (igual que `Employee.position`) en vez de un desplegable contra un catálogo de vacantes: crear una entidad "Vacante" aparte habría duplicado casi todo lo que ya describe un puesto + departamento, para un beneficio marginal en este alcance deliberadamente ligero. La **fase** sí es una lista cerrada (`CANDIDATE_PHASES`) en vez de un catálogo editable como los tipos de día, las plantillas de documentos o las tareas de incorporación: a diferencia de esos tres, las fases de un proceso de selección son universales entre empresas, no varían de una a otra, así que añadir una pantalla de gestión propia solo habría sido complejidad sin beneficio real. El email del candidato, a diferencia del de un empleado, no lleva `UNIQUE`: reaplicar con el mismo email a otra vacante (o a la misma más adelante) es un caso legítimo, no un error de captura.
- Un departamento con un usuario (encargado) todavía asignado tampoco se puede eliminar, igual que con empleados o candidatos — pero por una vía distinta: `users.department_id` es `ON DELETE SET NULL` (a propósito, no `RESTRICT`: quitarle el departamento a un usuario no le hace perder la cuenta, solo el ámbito), así que `IntegrityError` nunca salta para este caso y el `try`/`except` genérico que basta para empleados/candidatos no lo detecta. `DepartmentRepository.delete()` comprueba `has_users` de forma explícita antes de intentar el borrado, en vez de asumir que cualquier bloqueo se manifiesta como una excepción. La restricción por rol (un encargado no gestiona departamentos) se comprueba, a propósito, en dos sitios a la vez: el acceso rápido de Inicio (la tarjeta "Departamentos" directamente no se construye para un encargado) y el propio método que abre la gestión de departamentos (se niega a abrirse igual, por si algo más lograra invocarlo) — el mismo patrón "cinturón y tirantes" ya aplicado a que un usuario no pueda eliminar su propia cuenta (bloqueado en el diálogo y en `UserRepository.delete()`) y a que un empleado ya anonimizado no pueda editarse (botones deshabilitados en la ficha y el propio repositorio lo rechaza si algo los sortea).
- `employees.manager_id` es una clave foránea **a la propia tabla** (`REFERENCES employees(id) ON DELETE SET NULL`) — confirmado empíricamente con un script suelto que SQLite acepta y hace cumplir una auto-referencia igual que cualquier otra FK, tanto vía `ALTER TABLE ADD COLUMN` (para bases de datos ya existentes) como al insertar/actualizar filas. `EmployeeRepository` la valida en tres capas antes de guardarla: el supervisor propuesto debe pertenecer al mismo departamento (mismo criterio que ya existía para `shift_id`), debe estar activo, y no puede cerrar un ciclo. Esto último (`_would_create_management_cycle()`) recorre hacia arriba la cadena de supervisores YA guardada partiendo del candidato propuesto: si en algún punto se llega al propio empleado que se está editando, la asignación se rechaza — cubre tanto la auto-asignación directa (un ciclo de longitud cero) como una cadena indirecta (A supervisa a B, B supervisa a C, y se intenta hacer que A dependa de C). La comprobación de ciclos solo se ejecuta al editar un empleado ya existente, nunca al crear uno nuevo: un id recién creado no puede tener nadie por debajo todavía, así que ninguna asignación de supervisor en el alta puede cerrar un ciclo, sin necesidad de comprobarlo.
- El árbol del Organigrama (`OrgChartPage`) solo incluye empleados **activos** — quien ya no trabaja aquí no aporta nada a "cómo está organizado el equipo hoy" — y trata a un supervisor que quedó fuera de ese conjunto (de baja, o sin asignar) como si no existiera: quien le reportaba pasa a mostrarse como raíz, nunca como huérfano oculto ni como fallo. La construcción del árbol lleva su propio conjunto de nodos visitados aunque la creación de ciclos ya esté bloqueada en el repositorio — una segunda red de seguridad barata para que esta pantalla nunca entre en una recursión infinita si algún día un dato llegara corrupto por otra vía (edición manual de la base de datos, por ejemplo), no una comprobación que se espere disparar nunca en el uso normal.
- `employees.head_of_department_id` (FK a `departments`, `ON DELETE SET NULL`) es un campo deliberadamente independiente y sin ninguna relación con `manager_id` ni con el rol `encargado` de `User` — un tercer concepto distinto, no una forma alternativa de expresar los otros dos. `manager_id` exige mismo departamento, empleado activo, y rechaza ciclos, porque describe una relación de supervisión real dentro de la jerarquía del organigrama; `head_of_department_id` no tiene ninguna de esas restricciones (validado solo por existencia del departamento, igual que `department_id`/`shift_id`) porque es puramente descriptivo — quién encabeza qué departamento, ni siquiera necesariamente el suyo propio — y no participa en ningún árbol ni cálculo. Marcarlo **no** crea, modifica ni elimina ninguna cuenta de usuario ni cambia ningún permiso: `User.role == "encargado"` (con su propio `department_id`, ver "Inicio de sesión y usuarios") sigue siendo la única vía real que controla qué ve cada quien en la aplicación, completamente aparte y sin ningún vínculo estructural con `Employee` (no existe `employee_id` en `User` ni `user_id` en `Employee`, a propósito, según lo pedido explícitamente al implementar esto).
- Un curso de formación y una certificación se guardan en una única entidad (`EmployeeTraining`, tabla `employee_trainings`), no en dos formularios ni dos tablas separadas: la única diferencia funcional entre ambos es si caduca, y una `expiration_date` opcional (con su casilla "No caduca", marcada por defecto) ya lo capta sin necesitar un campo de tipo redundante que además habría que mantener sincronizado con esa misma casilla. A diferencia de un accidente de trabajo o de la formación PRL obligatoria, cuya fecha no puede preceder al ingreso porque describen hechos ocurridos ya *en* el puesto, `completion_date` no lleva esa restricción: un carné, un idioma o una titulación técnica puede haberse obtenido años antes de empezar a trabajar aquí, así que solo se rechaza una fecha futura. La alerta de caducidad (`training_expiry_alerts()`) genera un aviso por **registro**, no por empleado, a diferencia de las demás: quien tenga varias certificaciones venciendo en fechas distintas necesita ver cada una por separado, no un único aviso agregado que oculte cuál de ellas es la que realmente caduca. Sigue el mismo precedente que `retention_review_alerts()` al no integrarse en `all_alerts()` — necesita la lista de formaciones además de la de empleados, un parámetro extra que el resto de funciones de alerta no requiere — así que cada llamador (`alerts_ui.py`, el resumen semanal de `main.py`) la invoca aparte y combina el resultado a mano. `email_digest.py` resultó tener su propio diccionario `_CATEGORY_LABELS`, separado del de `alerts_ui.py` y no compartido con él: los dos necesitaron la misma entrada nueva (`"certificacion": "Certificación"`) por separado, una duplicación ya existente desde antes (no introducida ahora) que quedó al descubierto al añadir esta categoría.
- Convenios colectivos (`CollectiveAgreement`) y categorías profesionales (`ProfessionalCategory`, con su `minimum_salary`) son dos entidades nuevas y independientes, no un único catálogo plano: una categoría (`professional_categories.collective_agreement_id`, `ON DELETE CASCADE`) no tiene sentido fuera de su convenio, igual que un turno no lo tiene fuera de su departamento — mismo precedente ya usado por `shifts.department_id`, confirmado antes de escribir la migración en vez de asumido. `employees.professional_category_id` (FK a `professional_categories`, `ON DELETE SET NULL`) sigue en cambio el precedente de `employees.shift_id`, no el de `employees.department_id`: es un dato de clasificación opcional que no bloquea nada si desaparece, así que eliminar una categoría en uso simplemente desasigna a quien la tuviera en vez de impedir el borrado — a diferencia de un departamento o un turno con asignaciones reales en el calendario, aquí no hay ningún dato operativo que se pierda. El nombre de una categoría es único dentro de su propio convenio (`UNIQUE(collective_agreement_id, name)`) pero se puede repetir libremente entre convenios distintos — dos convenios distintos pueden tener cada uno su propio "Oficial de primera" con salarios mínimos distintos, sin colisionar.
- El **puesto** de un empleado (texto libre) no se sustituye por la categoría profesional, conviven como dos datos independientes: el puesto describe qué hace la persona en el día a día, la categoría es su clasificación formal a efectos de convenio — mismo criterio de "añadir, no sustituir" ya aplicado a `head_of_department_id` frente al puesto/rol existentes. Por eso el desplegable de categoría se colocó justo debajo de Puesto en la ficha, no junto a Departamento/Turno con el resto de campos organizativos.
- Esta primera versión deliberadamente **no** compara el salario de nadie contra el mínimo de su categoría ni genera ninguna alerta si queda por debajo, aunque el dato (`minimum_salary`) ya está guardado y listo para ello: el propio texto del punto de la hoja de ruta lo enmarca como algo que esto "permitiría **más adelante**", no como parte de este alcance — a diferencia de Organigrama o de Encargado de departamento (que si necesitaron una pregunta de aclaración por tener un fork genuino de alcance), aquí el propio texto ya resolvía la ambigüedad sin necesidad de preguntar. Añadir esa comparación ahora habría sido construir una función no pedida todavía, con el riesgo añadido de una alerta de nómina mal calibrada — el mismo motivo, por prudencia, por el que el desglose de IT o el cálculo de nómina llevan su propio disclaimer en vez de presentarse como más autoritativos de lo verificado.
- El autoservicio del empleado se implementó como **email + PIN de 4-6 dígitos**, no como una cuenta de usuario real con su propio rol — una elección explícita del usuario (frente a la alternativa de un tercer rol `User.role == "empleado"`), coherente con que esta app es de uso personal y con que el propio texto del punto de la hoja de ruta lo describe como "una vista mínima de solo lectura". El PIN se guarda con el mismo hash PBKDF2 + sal por persona que las contraseñas de `User` (reutilizando `_hash_password()`, no un segundo esquema de cifrado), y `Employee` (el modelo) no expone `self_service_pin_hash`/`self_service_pin_salt` en absoluto — ni en `_row_to_employee()`, ni en la ficha, ni en la exportación RGPD — exactamente igual que `User.password_hash`/`salt` nunca salen de `UserRepository`. `authenticate_self_service()` sigue además la misma postura de `UserRepository.authenticate()`: ni el email ni el PIN se validan antes de comparar (un intento con formato inválido simplemente no encuentra coincidencia, sin revelar si falló el email o el PIN), y la comparación del hash usa `hmac.compare_digest` (tiempo constante), no `==`.
- A diferencia de cambiar la propia contraseña (autoservicio real, sin registro de auditoría porque cada usuario actúa sobre su propia cuenta), establecer o quitar el PIN de otra persona es una acción de RRHH sobre la ficha de un tercero — el mismo tipo de acción que crear o eliminar un usuario — así que sí queda en el registro de auditoría. Solo empleados **activos** con un PIN ya asignado pueden autenticarse: alguien de baja pierde el acceso automáticamente en el momento en que se le da de baja, sin ningún paso adicional de "quitarle el PIN" — la comprobación de `active = 1` vive en la propia consulta de `authenticate_self_service()`, no como un filtro añadido después.
- La vista de autoservicio es deliberadamente de **solo lectura**: reutiliza `vacation.calculate_balance()`, `PayrollRecordRepository.list_for_employee()` y `TimeEntryRepository.list_for_month()` tal cual (las mismas funciones puras/repositorios que ya usan la ficha y las páginas de nóminas/fichajes), sin ninguna ruta de escritura propia — ni fichar (eso conserva su modo kiosco ya existente, `TimeClockPage`), ni editar ningún dato. `EmployeeAccessDialog` (el acceso por email+PIN) y `LoginWindow` (usuario/contraseña de admin/encargado) son dos flujos completamente independientes que conviven en la misma ventana inicial: uno no interfiere con el otro, y ninguno de los dos necesita saber que el otro existe.
- `Objective` y `PerformanceReview` son dos entidades independientes, no una sola tabla con un campo "tipo": un objetivo mira hacia adelante (fecha límite + estado, la fecha objetivo admite tanto futuro como pasado — un backfill de un objetivo que se olvidó dar de alta a tiempo es legítimo, a diferencia de casi cualquier otra fecha de esta app) y una evaluación es una nota de seguimiento sobre algo ya ocurrido (fecha que no puede ser futura, comentario libre sin plantilla de puntuación fija) — forzarlas en una tabla común habría violado el mismo criterio de "que los estados imposibles no se puedan representar" ya aplicado a mantener separados un episodio de IT y una simple ausencia "Enfermedad". Cambiar el estado de un objetivo es una acción propia (`ObjectiveRepository.update_status()`), no una rama de un `update()` genérico — mismo patrón que dar de baja a un empleado o marcar un equipo como devuelto: título y fecha objetivo no se editan en el sitio, si están mal se elimina el objetivo y se crea de nuevo.
- `AssignedEquipment.description` es texto libre (igual que `Employee.position` o el título de un objetivo), no un desplegable contra un catálogo de tipos de material: la variedad real de objetos que se entregan (portátil, móvil, llaves, tarjeta de acceso...) no encaja en una lista cerrada sin quedarse corta tarde o temprano. La fecha de devolución hace de estado implícito (`NULL` = todavía en manos del empleado) en vez de un campo `estado` aparte que pudiera desincronizarse de ella; marcarlo devuelto es una acción propia (`mark_returned()`, rechaza una fecha anterior a la de entrega y rechaza marcarlo devuelto dos veces) igual que cambiar el estado de un objetivo, mientras que la descripción y la fecha de entrega no se editan en el sitio. La regla "la devolución no puede ser anterior a la entrega" se aplica **dos veces**, no solo en Python: también como `CHECK` a nivel de base de datos (`CHECK (returned_date IS NULL OR returned_date >= assigned_date)`), verificado empíricamente que salta `IntegrityError` incluso saltándose la capa de validación con SQL directo — mismo criterio de "cinturón y tirantes" que `dependent_children >= 0`.
- Aplicar una rotación de turnos (`DailyAssignmentRepository.apply_rotation_to_range()`) cicla la posición dentro de la secuencia elegida día a día y **envuelve** ('wrap') tantas veces como haga falta para cubrir el rango — a diferencia de `apply_shift_to_range()` (un único turno, que sí respeta su propio `days_of_week`), aquí es el orden en el que se añadieron los elementos al patrón el que decide qué toca cada día, sin mirar el patrón semanal de nada: un turno rotativo real (ej. hospitalario, 4 días de mañana - 2 de descanso) no sigue un patrón por día de la semana, sigue una cuenta de días consecutivos. Deliberadamente **no** se guarda el patrón como una entidad "plantilla" reutilizable, solo su resultado día a día — el propio punto de la hoja de ruta no pedía poder reutilizar patrones guardados entre aplicaciones distintas, así que añadir esa persistencia habría sido construir algo no pedido. La validación (empleado y cada turno distinto del patrón) ocurre **antes** de escribir nada, no durante el bucle día a día: un turno inexistente en mitad de un patrón de varios elementos se rechaza sin dejar ningún día ya escrito a medias, verificado explícitamente con un patrón que combina un turno válido y uno inexistente.

- El logging (`app/logging_config.py`) nunca sale de este ordenador: es un archivo local con rotación, sin ningún servicio externo. Cubre dos fuentes de excepciones no controladas por separado porque Tkinter las trata de forma distinta: `sys.excepthook` para lo que pasa **fuera** del bucle de eventos (arranque, antes de que exista ninguna ventana), y `Tk.report_callback_exception` — sustituido a nivel de **clase**, no en cada ventana por separado, así cubre tanto `LoginWindow` como `MainWindow` con una sola llamada — para cualquier excepción **dentro** de un callback (clic de botón, atajo de teclado). Sin el segundo, una excepción en un callback de la versión compilada `--windowed` simplemente desaparecía: por defecto Tkinter solo la imprime a stderr, y esa versión no tiene consola donde verlo. Aviso honesto, no escondido: como algunos mensajes de error de este proyecto ya incluyen a propósito el valor concreto que falló (ej. "ya existe un empleado con el email 'x'"), un log de una excepción de ese tipo podría heredar ese mismo valor — el archivo de log recibe el mismo nivel de confianza que `backups/`, nunca sale de la carpeta de instalación.

Deliberadamente **no** incluye el mensaje ni la traza de la excepción — a diferencia del log local, que nunca sale de este ordenador, un correo sí sale, y algunos mensajes de error de este proyecto incluyen a propósito un valor identificativo real; el correo solo dice el tipo de excepción y cuándo ocurrió, y remite al log local para el detalle. El envío ocurre en un hilo `daemon` aparte para no congelar la ventana mientras se conecta al SMTP — un fallo real ya es mal momento para que, encima, la interfaz se quede sin responder varios segundos.
